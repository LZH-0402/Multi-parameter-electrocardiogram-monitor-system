# P6-V 云端 AI 语音对话总体开发合同与系统方案

> **文件编号**：MPM-P6-V-SOW-001  
> **版本/日期**：v1.0｜2026-10-12  
> **项目**：多参数生理监护仪系统工程样机  
> **设计基线**：P4 当前合并基线 `67f5f57bd82c6e326e9e78ec9540481c80105e5f`（已包含 P5 coreMQTT 迁移）  

## 1. 总体目标与项目定位

在保留现有 STM32F407 三节点、CANopen、Gateway-C、ESP8266、MQTT 3.1.1/TLS、腾讯云和 Web 大屏主链路的基础上，新增**实体网关语音对话能力**：使用设备侧麦克风提问，通过 Gateway-C 上云，由云端语音识别与豆包模型生成回答，再将**同一份回答**显示在监护大屏 AI 区域，并下发 Gateway-C，由 **TW-TTS V1.0 + 外接喇叭**播报。

本阶段**不引入 FreeRTOS，不以 AI 取代监护或医疗诊断功能**。AI 是监护数据查询、设备说明与健康科普辅助模块，监护系统脱离 AI 仍可独立运行。

## 2. 功能需求与阶段范围

| 业务能力 | P6 总体需求 | 设计边界 |
|---|---|---|
| 设备端语音输入 | Gateway-C 外接麦克风，采集现场用户的问题 | 麦克风型号尚未选定；音频上云可行性需先验证 |
| 云端语音理解 | 专用 ASR 将音频转换为问题文本；**豆包**完成问答 | ASR 与文本大模型是两个服务能力，不把二者混为一项 API |
| 读取监护数据 | 读取 Backend 已判定有效的 HR、SpO2、NIBP、TEMP 等当前信息 | INVALID、STALE、OFFLINE、MOCK、REPLAY 不得冒充实时实测 |
| AI 适度建议 | 支持体温偏高等场景下的一般性科普或复测提醒 | 不作疾病诊断、开药、紧急医疗决策或自动控制硬件 |
| 双端回答 | 文字显示在现有 Web 大屏的 AI 按钮/独立区域，同时下发网关本地播报 | 显示文字与播报文本应保持一致、可区分失败状态 |
| 会话操作 | 大屏可开启/结束对话，设备侧保留明确工作状态 | 按需开启、非全天候无提示监听；单人轮流对话优先 |

**本阶段不强制完成**：多模态模型、多人同时抢答、免唤醒连续对话、云端 MP3 流播放、临床决策支持、语音远程控制 NIBP 泵阀、全系统 RTOS 改造。

## 3. 系统总体架构

![图 V1：沿用现有监护链路并新增设备端双向语音](assets/A1_P6云端AI总体架构.png)

上图划分为两条相互隔离的业务链路：

- **原监护主链路**：Node-A/B → CANopen → Gateway-C（STM32F407 + ESP8266）→ MQTT/TLS → 腾讯云 Broker / Backend → Web 大屏。此链路继续沿用已验证的协议与显示方式。
- **新增语音链路**：设备侧麦克风 → Gateway-C → ESP8266 网络出口 → 腾讯云语音服务（ASR + 豆包 + 可信监护摘要）→ 回答文字双路分发。一路到大屏 AI 区域，另一路经限定 MQTT 下行回到 Gateway-C → TW-TTS V1.0 → 喇叭。

云端 AI 组件应作为**独立功能服务**接入现有腾讯云环境。模型接口故障、识别失败或播报忙碌，不应阻断 CANopen 汇聚、原有 MQTT 遥测和 Web 实时监护。

### 总体对话流程

![图 V2：从板端提问到双端回答的总流程](assets/A2_云端对话总体流程.png)

设计原则为**先校验数据再回答，先保证文本可靠，再使设备播报**。用户从大屏开启或关闭会话；AI 回答只建立在已知有效的指标和项目资料之上。模型不能自行修改设备状态、报警阈值或传感器数值。

## 4. 协议与技术选型原则

| 层级 | 规划采用的成熟方案 | 选型理由 |
|---|---|---|
| Node-A/B 与 Gateway-C | **CANopen over CAN** | 保留原工业现场总线与对象字典，不设计另一套板间协议 |
| Gateway-C 与腾讯云 | **MQTT 3.1.1 over TLS**，复用 ESP8266 | 原链路已落地；语音功能另设业务通道，原遥测 Topic/语义不变 |
| 云端业务与 AI | Python/FastAPI 及专用语音服务；火山语音 ASR + 火山方舟**豆包** API | 复用现有 Python 后端生态，外部模型由服务端集中调用 |
| 云端与 Web | **HTTPS / WebSocket**；Vite + TypeScript + 原生 DOM/Canvas | 在既有大屏增加 AI 区域，无需重做前端框架 |
| Gateway-C 与播报模块 | **UART → TW-TTS V1.0 → 8Ω 喇叭** | 使用现有实物播报板；其协议按 TW-TTS 手册而非 SYN6288 处理 |

> **尚需专题可行性评审的两个问题**：① 现有 ESP8266 网络出口及 F407 资源能否同时承载监护与压缩语音上行；② 当前 Gateway 只按既有遥测/确认路径运行，下行 AI 文字需新增经白名单限制的接收能力。**本总合同只确定业务方向，不预先签发具体音频编码、串口引脚、Topic 字节布局或固件改动。**

## 6. 开发阶段与里程碑（总规划）

| 阶段 | 核心目标 | 阶段产出 |
|---|---|---|
| **V0 · 方案与外设可行性** | 选定麦克风方向；确认资源、带宽、TW-TTS 与板卡接口 | 冻结可行的设备语音总体架构，明确阻断和备选路线 |
| **V1 · 文本双端闭环** | 云端文字提问、豆包回答、大屏显示、网关 TW-TTS 播报 | 在不改变监护主链路条件下形成可演示的文本回答闭环 |
| **V2 · 设备语音上云** | 实现设备录音、云端 ASR 和同一回复的双端分发 | 完整的“人说话—云端理解—两端回答”功能 |
| **V3 · 系统协同验证** | 多参数查询、失效数据过滤、网络异常与降级展示 | 阶段测试记录、风险结项建议，为 P6 综合展示提供基础 |

V0 是**技术可行性关口**：若原通信链路无法在保留监护能力时可靠承载语音，本阶段应先评审架构调整，而不是暗中加入第二主控或覆盖 P4 已验收代码。

## 7. 总体验收与风险管理

本功能线是否达到总体目标，重点观察：设备侧能发起并结束对话；云端能识别问题、调用豆包并读取可信监护摘要；同一回答能够**在大屏显示且由本地喇叭播报**；音频/云服务不可用时，四传感器监护、Gateway-C 和原有 Web 不受新增功能阻断。

主要风险包括**语音与监护共用网络资源、麦克风尚未选型、模型可能编造指标、下行权限与旧 MQTT 逻辑不兼容**。这些风险在详细设计与专项联调中分别验证；不把总体方案等同于“设备端语音已验收”。

## 8. 设计冻结与变更管理

本合同在评审通过后拟冻结：**设备侧双向对话、STM32F407 唯一主控、ESP8266 原网络出口、豆包云端模型、TW-TTS 本地播报、双端同文展示、既有 P4 监护业务不变**。

以下事项需另行签发详细开发合同后才能实施：麦克风与供电/串口引脚、语音带宽/编码及 MQTT 下行业务处理、模块焊接与烧录、云账户凭据配置、生产切换、安全门和真机测试。**本文件仅用于总体方案评审，不授权任何仓库写入、硬件操作或采购。**
